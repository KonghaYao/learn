## 一句话

一个文件一个概念。
先给概览，再给细节。
短句、短段、左对齐。

## 怎么读这份规范

每条规则带一个证据标记：

| 标记 | 意思 |
|---|---|
| `[强]` | 系统综述或多个实验一致支持 |
| `[中]` | 单项实验或权威指南支持 |
| `[有限]` | 专家共识或证据较弱 |
| `[约定]` | 本库选择，不声称是论文结论 |

证据、原文引语和争议见 [证据页](/meta/evidence)。

不要把 `[约定]` 写成“研究证明”。
这是这份规范最重要的规则。

## 分工

| 谁 | 做什么 |
|---|---|
| 用户 | 提供方向、纠正理解、确认不确定的选择 |
| AI | 启动、写、整理、更新索引、记录日志和调整 |

默认由 AI 动手。
用户不需要复制模板、建目录或改索引。

## 1. 文件命名

证据：`[约定]`

| 类型 | 规则 | 例子 |
|---|---|---|
| 结构目录 | 英文小写 | `notes/` |
| 主题目录 | 中文短名 | `notes/方法/` |
| 笔记 | 中文短名 | `如何写一条笔记.mdx` |
| 日志 | 日期 | `2026-11-04.mdx` |
| 附件 | 英文小写加连字符 | `closure-diagram.png` |

规则：

- 不用空格，用 `-`。
- 不用特殊符号。
- 名字要能一眼看懂。
- 改名后，更新索引和相关链接。

## 2. Frontmatter

证据：`[约定]`

每篇发布区页面开头：

```yaml
---
title: 如何写一条笔记
description: 一条笔记只讲一件事。
date: 2026-11-04
tags: [方法, 写作]
status: growing
---
```

字段：

| 字段 | 必填 | 说明 |
|---|---|---|
| `title` | 是 | 页面标题，也是 H1 |
| `description` | 是 | 一句话总结 |
| `date` | 建议 | 创建或更新日期 |
| `tags` | 否 | 关键词 |
| `status` | 是 | seed / growing / evergreen / archived |

注意：

- 正文不要再写一次 H1。
- 标题由 Nimbus 从 `title` 生成。

## 3. 笔记结构

笔记分三层。
每层的作用不同，证据也不同。

| 层 | 写什么 | 作用 | 证据 |
|---|---|---|---|
| 5 秒版 | 一句话 | 检索线索，帮你找到它 | `[约定]` |
| 1 分钟版 | 最多 3 条 | 帮你决定要不要继续读 | `[约定]` |
| 深入版 | 为什么 / 怎么做 / 如果…… | 自我解释：用自己的话重述定义 | `[中]` |
| 例子 | 一个具体例子 | 让抽象概念落地 | `[约定]` |
| 自测（可选） | 2–3 个问题 | 检索练习 | `[强]` |
| 还没懂 | 留问题 | 下次学习的入口 | `[约定]` |
| 相关 | 链接 | 建立连接 | `[约定]` |

写法：

- 5 秒版只写一句。
- 1 分钟版不超过 3 条。
- 例子优先于定义。
- “我的理解”必须用自己的话。
- “还没懂”可以留空，但不要删掉标题。
- 自测问题可以留空；复习机制暂缓。

完整模板见 `templates/note.mdx`。

## 4. 链接

证据：`[约定]`

用根相对路径：

```md
[如何写一条笔记](/notes/方法/如何写一条笔记)
```

不要用：

```md
[如何写一条笔记](../方法/如何写一条笔记)
```

原因：

- Nimbus 的检查规则默认不允许相对链接。
- 根相对路径在站点里更稳定。

## 5. 主题目录

证据：`[约定]`

按需创建。

第一次出现某个主题时：

1. AI 建 `src/content/docs/notes/<主题>/`。
2. AI 复制 `templates/topic-index.mdx`，存成 `index.mdx`。
3. AI 在 `notes/index.mdx` 加一行。
4. AI 再放笔记。

建好后，顶栏会自动出现这个领域。
不需要改 `Header.astro`。

不要提前建一堆空目录。

## 6. 整理 inbox

证据：`[约定]`

AI 每周整理一次。

对每条：

- 有用：写成笔记。
- 没用：删除。
- 不确定：留着，标上日期，问用户。

不要追求一次整理完。

## 7. 学习闭环

| 步骤 | 做什么 | 证据 |
|---|---|---|
| 捕获 | 先记下来 | `[约定]` |
| 整理 | 用自己的话写 | `[中]` 自我解释 |
| 举例 | 给一个具体例子 | `[约定]` |
| 自测 | 留 2–3 个问题 | `[强]` 检索练习 |
| 间隔 | 以后需要时回看 | `[强]` 间隔练习；本库暂缓 |
| 连接 | 链到已有笔记 | `[约定]` |

重读和划重点，不作为主要的学习方式。
原因是它们的效用较低（Dunlosky et al., 2013，转述）。

## 8. 阅读友好规则

### 8.1 有指南或研究支持

| 规则 | 证据 | 说明 |
|---|---|---|
| 正文 16–19px | `[中]` | 当前站点 16px，落在 BDA 范围内 |
| 中文行高 1.75–2.0；英文 1.6 | `[中]` | 当前站点 1.75 |
| 左对齐，不两端对齐 | `[有限]` | 两端对齐会让词间距不均 |
| 只用加粗强调 | `[中]` | 不用斜体、下划线、全大写 |
| 句子短 | `[有限]` | BDA 建议短句；英文 60–70 字符讲的是句子。中文 25–40 字是本库约定 |
| 标题比正文大至少 20% | `[有限]` | 层级要连续 |
| 术语首次出现时解释 | `[中]` | 并提供术语表 |
| 先给概览，再展开 | `[有限]` | 每个新章节也给概览 |

注意：
“60–70 字符”讲的是**句子长度**，不是每行字符数。
不要把它当成行长依据。

### 8.2 本库约定

| 规则 | 说明 |
|---|---|
| 一段不超过 3 行 | 设计约定，不是实验结论 |
| 行长约 25–30 个汉字 | 设计约定；不要引用 BDA 60–70 来证明 |
| 标题不超过 3 层 | 设计约定 |
| 列表建议 ≤7 条 | 设计约定；不要引用 7±2 |
| 重点只标关键词 | 设计约定；BDA 支持“用加粗强调” |
| 长内容先放 5 秒版 | 设计约定 |

### 8.3 不要写

- 不要写“WCAG 要求行距 1.5”。
  WCAG 要求的是用户调大间距后内容不坏。
- 不要把 BDA 的“60–70 characters”说成每行字符数。
  原句主语是句子。
- 不要用 7±2 证明“列表 ≤7 条”。
- 不要说“原子笔记有实验证明”。
  它是实践约定。

## 9. 文风

底座是[基础风格指南](/meta/style-base)：用户优先、认受众、术语一致、译意不译词、语气清楚。
本节是执行细则。

依据：ISO 24495-1:2023、GOV.UK 写作规范、美国 Federal Plain Language Guidelines。

这三份都是写作规范，不是实验。
多来源一致，只说明“写作规范有共识”，不说明“这样写能提高成绩”。
证据标 `[中]`。

中文一侧只核验到余光中的评论文章。
标 `[有限]`，不算研究证据。

### 9.1 八条规则

| 规则 | 证据 | 说明 |
|---|---|---|
| 一句一个主张 | `[中]` | 出现两层对比、连用几个“的”、读完要回头，就拆开 |
| 让动作回到动词 | `[中]` | 删掉“进行”“作出”“加以”“受到”和空转的“……化” |
| 默认主动，写明谁做什么 | `[中]` | 不知道谁做，或结果比执行者重要时，才用被动 |
| 段首给结论，一段一件事 | `[中]` | 第一句单独读，也应该是这段的摘要 |
| 旧信息在前，新信息在后 | `[中]` | 用“这一点”“该问题”回指上一句 |
| 术语首现即解释 | `[中]` | 写成“中文术语（English term，缩写）＋一句白话” |
| 对读者说“你”，对自己说“我” | `[中]` | “我们”第一次出现时，说明指谁 |
| 按读者需要删，不按字数删 | `[中]` | 标准是读者能否找到、看懂、用上 |

“受到”“加以”“……化”是把同一原则套到中文。
这一部分是本库约定，标 `[约定]`。

### 9.2 改法示例

| 原句 | 改后 | 改了什么 |
|---|---|---|
| 我们对数据进行了分析。 | 我们分析了数据。 | 去名词化 |
| 该方案受到了很多质疑。 | 很多人质疑该方案。 | 主动语态，补出执行者 |
| 本文对该问题进行了深入的讨论。 | 本文深入讨论了这个问题。 | 去名词化 |
| 实验结果表明，该假设是可以成立的。 | 实验结果表明，这个假设成立。 | 删冗余判断句 |

例子是本库自己写的，用来说明规则，不是引语。

### 9.3 长度

不设“每句不超过 X 字”的硬指标。

英文机构的口径本身就不一致。
GOV.UK 建议拆开超过 25 词的句子。
美国指南给的是每段 3–8 句、上限 250 词。

这些是实践约定，不是实验结论。
本库的做法：

- 一段超过 3 行，先拆。
- 一句话读完要回头，先拆。
- 拆完信息没少，就保留拆后的版本。

### 9.4 语气

- 直接，但不冷硬。
  GOV.UK 的原话是 “brisk, but not terse”。
- 不用“值得注意的是”“综上所述”这类填充。
- 友好让位给准确。
  不确定就写不确定。

### 9.5 不要写

- 不写“进行了……”“作出了……”“加以……”“受到……的影响”这类空转结构。
- 不把“……性”“……化”堆成名词串。
- 不用否定缩约形式（can’t、don’t）。
  GOV.UK 的理由是读者容易读反；这条在本库算 `[约定]`。
- 不用“不是 X，而是 Y”的对偶句式。
  直接陈述结论，或把否定单独写成一句。
- 专有名词按[术语与译名表](/meta/glossary)处理：Agent、subagent、harness、worktree、skill、playbook 不译；feedback loop 译“反馈循环”，deep module 译“深度复杂模块”，frontier 译“前沿”。
- 不为了短而删掉读者需要的信息。
- 不把写作规范说成实验结论。

## 10. 发布区与工作区

工作区：

- `inbox/`
- `templates/`
- `CLAUDE.md`
- `AGENT.md`

发布区：

- `src/content/docs/`

规则：

- 不把草稿直接放进发布区。
- 不把密钥、密码、个人隐私写进仓库。

- AI 可以写和整理。
- 发布、部署和 Git 提交需要用户明确同意。

## 12. 证据与引用

证据：`[约定]`

写规范、改规则、引用研究时：

1. 先分清研究证据和实践约定。
2. 直接引语必须逐字准确。
   - 用 blockquote。
   - 注明作者、年份、章节和链接。
   - 省略用 `[...]`。
3. 转述不要放进引号。
   - 写“据……的综述/研究”。
4. 未核验的来源要标 `未核验`。
   - 不编造页码、DOI 或作者。
5. 每条规范尽量带证据标记。
6. 证据细节放 [证据页](/meta/evidence)。
